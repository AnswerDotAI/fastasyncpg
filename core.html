fastasyncpg

fastasyncpg is a simple wrapper for asyncpg. We’ll explain how it works and build up the module in a “literate” nbdev style.

Installation

On macOS, the recommended way to install PostgreSQL is via Homebrew. Other options include Postgres.app (a menubar app) and the EDB installer, but Homebrew integrates best with command-line workflows and makes updates simple.

To install PostgreSQL 18 (the current latest stable release):

brew install postgresql@18

To check if you already have PostgreSQL installed via Homebrew, run brew list | grep postgres. You can also check which version is in your PATH with psql --version.

Let’s verify the installation is working:

!brew list | grep postgres
!psql --version
postgresql@18
psql (PostgreSQL) 18.4 (Homebrew)

After installation, run brew info postgresql@18 to see setup instructions. PostgreSQL 18 is “keg-only”, meaning it’s not automatically symlinked into your PATH.

You’ll see something like:

This formula has created a default database cluster with:
  initdb --locale=en_US.UTF-8 -E UTF-8 /opt/homebrew/var/postgresql@18

When uninstalling, some dead symlinks are left behind so you may want to run:
  brew cleanup --prune-prefix

If you need to have postgresql@18 first in your PATH, run:

To start postgresql@18 now and restart at login:
  brew services start postgresql@18

Connecting with Python

The most popular Python libraries for PostgreSQL are psycopg2/psycopg3 (synchronous) and asyncpg (async). For async work, asyncpg is about 5x faster than psycopg3 and is the recommended choice.

We’ll use asyncpg for this wrapper — it’s the fastest Python PostgreSQL library for async code.

from fastcore.test import expect_fail,test_eq
from unittest.mock import patch as mock_patch
user = os.environ['USER']; user
'jhoward'

asyncpg uses await for all database operations. The connect function returns a connection object, and fetchval is a convenience method that returns a single value from the first row:

conn = await asyncpg.connect(user=user, database='postgres')
await conn.fetchval('SELECT version()')
'PostgreSQL 18.4 (Homebrew) on aarch64-apple-darwin25.4.0, compiled by Apple clang version 21.0.0 (clang-2100.0.123.102), 64-bit'

Let’s create a simple test table to explore basic operations:

await conn.execute('''DROP TABLE IF EXISTS users''')
await conn.execute('''CREATE TABLE users ( id SERIAL PRIMARY KEY, name TEXT NOT NULL, age INTEGER )''')
'CREATE TABLE'

Great! Now let’s insert some data:

await conn.execute("INSERT INTO users (name, age) VALUES ($1, $2)", 'Alice', 30)
'INSERT 0 1'

PostgreSQL uses $1, $2, etc. for parameterized queries, not ? like SQLite. This syntax allows you to reference the same parameter multiple times and makes the order explicit.

fetch returns a list of Record objects. Each record supports dict-like access by column name or index:

rs = await conn.fetch("SELECT * FROM users")
rs
[<Record id=1 name='Alice' age=30>]
r = rs[0]
type(rs),type(r)
(list, asyncpg.protocol.record.Record)

asyncpg.Record objects use dict-like access (r['name'] or r[0]), not attribute access. You can use dict2obj if you want the latter.

ro = dict2obj(dict(r))
ro.name
'Alice'

Unlike psycopg2, asyncpg doesn’t use traditional cursors. Instead, use async for record in conn.cursor(...) to iterate over results. However, cursors in asyncpg require an explicit transaction:

# raises "NoActiveSQLTransactionError: cursor cannot be created outside of a transaction"
# async for record in conn.cursor("SELECT * FROM users"): print(record)
async with conn.transaction():
    async for record in conn.cursor("SELECT * FROM users"): print(record)
<Record id=1 name='Alice' age=30>

By default, asyncpg operates in auto-commit mode — changes are applied immediately when not in an explicit transaction block. Regular queries (execute, fetch, etc.) don’t need transactions, but cursors do. This is a direct reflection of how PostgreSQL itself handles “portals” (the underlying mechanism for cursors).

In PostgreSQL, a portal is generally only valid for the duration of a transaction. If a transaction isn’t explicitly started, PostgreSQL runs each command in its own “one-shot” transaction. For a cursor to stay open so you can fetch multiple batches of rows, the transaction it belongs to must remain open.

Other libraries (like psycopg2) often hide this by starting a transaction for you automatically when you create a cursor, whereas asyncpg chooses to be more “explicit” about the underlying database state.

Chinook

For testing with a real dataset, we’ll use the Chinook sample database, which has tables for artists, albums, tracks, etc. The PostgreSQL version is available on GitHub:

Database wraps an asyncpg pool or connection and provides table/view metadata caching. It delegates unknown attributes to the current executor via __getattr__, so you can call db.fetch(...) directly. The conn property resolves that executor at call time: normally it’s the pool (or single connection) bound to the running event loop, but inside acquire/transaction (covered below) it’s the connection those context managers made current for the running task. Constructed with no arguments, a Database is unconnected – create it at import time as a module global, then attach a pool at app startup with connect (see the Connection pool section). The t property returns a _TablesGetter for convenient table access.

_Getter is a base class for “magic accessor” objects that provide multiple ways to access items — by attribute (dt.artist), by index (dt['artist']), or by iteration (for t in dt). It implements __dir__ so tab-completion works in notebooks, __repr__ for nice display, __contains__ for in checks, and both __getattr__ and __getitem__ for flexible access.

_TablesGetter specializes this for tables, reading from the database’s _tnames list. The db.t property returns one of these, giving you a clean API: db.t.artist instead of db.table('artist').

connect is our main entry point — it creates an asyncpg connection with FRecord as the default record class, sets up JSON codecs, and returns a Database wrapper with metadata already loaded:

async def connect(*args, **kwargs):
    kwargs.setdefault('record_class', FRecord)
    conn = await asyncpg.connect(*args, **kwargs)
    res = Database(conn, refresh=False)
    await res.refresh()
    return res

    SELECT * FROM a WHERE id = ?;

We get back values for the kwargs in the order they appear:

('SELECT * FROM artist WHERE artist_id = $1 AND name = $2', [5, 'AC/DC'])

A repeated kw placeholder name results in a single arg result:

conv_placeholders("SELECT * FROM a WHERE id = :uid OR creator = :uid", uid=42)
('SELECT * FROM a WHERE id = $1 OR creator = $1', [42])

Placeholder types can be mixed:

conv_placeholders("SELECT * FROM a WHERE id = ? AND name = :name and foo=?", name='test')
('SELECT * FROM a WHERE id = $1 AND name = $3 and foo=$2', ['test'])

The xtra method (defined earlier) lets you set persistent filters on a table. The _add_xtra helper injects these constraints into WHERE clauses. Connection pool

For production use, you’ll want a connection pool instead of a single connection. asyncpg.Pool has the same query methods (fetch, execute, etc.) as a connection, so Database works with both; the one pool-specific detail is that JSON codecs must be registered via the init callback, which runs on each new connection in the pool.

The recommended app pattern is a module-level db = Database() created unconnected at import time, with the pool attached at startup by connect. The object’s identity never changes, so everything that imports db – routes, helpers, background tasks – sees the connected database. Calling connect again closes any existing pool and swaps in a fresh one on the same object.

Pools are held per event loop (the async analogue of Django’s per-thread connections): connect binds a pool to the running loop, and close closes only that loop’s pool. A process with several loops – e.g. a notebook driving Starlette’s TestClient, whose app lifespan runs in its own loop – gets an independent pool per loop, and closing one leaves the others untouched.

Context managers

acquire

def acquire():

Make a single pool connection the current executor for this task

acquire doesn’t create a new object – it takes a connection from the pool, stores it in a ContextVar, and yields the same Database. Every query made while the block is active runs on that one connection, whether through db directly, a table object, or code called indirectly, because conn resolves through the ContextVar at call time. And since ContextVar is per-asyncio-task, concurrent tasks each get their own connection. This matters whenever several queries must share a connection: cursors, advisory locks, and above all transactions. If a connection is already current (or the database isn’t pool-backed), acquire is a no-op, so nesting is safe.

Queries inside the block all hit one server process (a stable pg_backend_pid), and the yielded handle is just db itself:

async with db.acquire() as sdb:
    assert sdb is db
    pids = [await db.fetchval('select pg_backend_pid()') for _ in range(2)]
test_eq(pids[0], pids[1])

transaction

def transaction():

Run the block in a transaction on a single connection, current for this task

transaction builds on acquire – it makes a connection current, starts a PostgreSQL transaction on it, and yields the database. Because the connection is ambient, everything inside the block joins the transaction: queries through db, table methods, even methods on objects fetched before the block. The as txn handle is db again, so use whichever name reads better – or none at all. Changes commit when the block exits normally, and roll back if it raises.

Here we verify that a failed operation rolls back the insert:

count_before = await db.t.artist.count
next_id = (await db.q("SELECT MAX(artist_id) as m FROM artist"))[0]['m'] + 1

try:
    async with db.transaction() as txn:
        await txn.t.artist.insert(artist_id=next_id, name='Test Artist')
        raise ValueError("something went wrong")
except ValueError: pass

count_after = await db.t.artist.count
test_eq(count_before, count_after)

And when the transaction succeeds, the changes are committed – this time using db directly inside the block, no handle needed:

count_before = await db.t.artist.count

async with db.transaction():
    await db.t.artist.insert(artist_id=next_id, name='Committed Artist')

count_after = await db.t.artist.count
test_eq(count_before+1, count_after)

await db.t.artist.delete(next_id);

One caveat: asyncio.create_task snapshots the current context, so a task spawned inside acquire or transaction inherits – and outlives – the block’s connection. Spawn background tasks outside these blocks.

Claiming items from queues

source

Table.claim

async def claim(
    where:NoneType=None, where_args:NoneType=None, order_by:NoneType=None, limit:int=1
):

Claim a row with SELECT … FOR UPDATE SKIP LOCKED (use inside a transaction)

claim is primitive that can be used to create queues: inside a transaction, it grabs one row matching a where clause and locks it until the transaction ends. Other transactions trying to claim simultaneously will skip past locked rows and grab the next available one — so you can run many workers against the same table without any of them stepping on each other.

To try it out we need a table with some kind of status column to filter on. Let’s set up a tiny jobs table with three pending rows:

class Job: id:int; payload:str; status:str

jobs = await db.create(Job, replace=True, defaults={'status': 'pending'})
await jobs.inserts([Job(payload='a'), Job(payload='b'), Job(payload='c')])

claim uses SELECT ... FOR UPDATE SKIP LOCKED, so two concurrent transactions get different rows – the second skips whatever the first has locked. This is what makes it safe for multiple workers to pull from the same queue without coordination. Since the current connection is per-task, we demonstrate with two tasks, using a Barrier to hold both transactions open until each has claimed. (Nesting db.transaction() within one task would instead give a savepoint on the same connection, which holds its own locks – so it would see the same row twice.)

bar = asyncio.Barrier(2)
async def _claim():
    async with db.transaction():
        res = await db.t.job.claim(where="status='pending'", order_by='id')
        await bar.wait()
        return res

async with asyncio.TaskGroup() as tg: tasks = [tg.create_task(_claim()) for _ in range(2)]
[t.result() for t in tasks]
[Job(id=1, payload='a', status='pending'),
 Job(id=2, payload='b', status='pending')]

def claim_one(

claim_one builds on claim by opening its own transaction and managing the row’s status. It yields a context object p whose .evt field holds the claimed row (or None if nothing was available). On normal exit the row’s status flips to 'completed'; on exception it’s marked 'failed' and the traceback is captured on p; setting p.retry = True skips the status update so the row stays 'pending'.

[Job(id=4, payload='a', status='completed')]

The statuses used by default are: ‘pending’, ‘completed’, and ‘failed’.

If an exception is raised, fail, tb, and exc are stored:

async with jobs.claim_one(order_by='id') as p:
    print(f"fail: {p.evt.payload}")
    raise ValueError("boom")
print(p.failed, p.exc)
fail: b
True boom

In addition, the item’s status is set to ‘failed’:

await(jobs("status!='pending'"))
[Job(id=4, payload='a', status='completed'),
 Job(id=5, payload='b', status='failed')]

When processing, set retry to have the item stay in ‘pending’ (in this case, you probably want a short sleep in your calling code if retry is set):

async with jobs.claim_one(order_by='id') as p:
    pl = p.evt.payload
    print(f"retry: {pl}")
    p.retry = True
retry: c
await jobs("payload=$1", [pl])
[Job(id=6, payload='c', status='pending')]

When the transaction is aborted the claimed event row is still set to failed:

await jobs.delete_where()
await jobs.inserts([Job(payload='repro', status='pending')])

async with jobs.claim_one(order_by='id') as p:
    await p.db.execute('select definitely_not_a_real_function()')
    await p.db.t.job.update(p.evt, status='processing')

test_eq(p.evt.status, 'failed')
test_eq(p.failed, True)

await jobs.delete_where()
await jobs.inserts([Job(payload='x', status='pending')])
